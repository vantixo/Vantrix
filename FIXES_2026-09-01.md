# Fixes — 2026-09-01

Three issues reported: chat scroll requiring manual "down navigation,"
character images appearing "half seen"/broken in chat, and no image on the
visitor (logged-out) homepage. All three are now fixed, typechecked,
linted, and the full test suite (506 tests) passes with zero regressions.

## 1. Character images "half seen" in chat

**File:** `src/components/chat/message-bubble.tsx`

**Root cause:** the photo/video thumbnail inside a chat bubble was forced
into a square (`aspect-square`) box with `object-cover`. Actual chat
photos are never square:
- In-chat photo generation defaults to Fal's `portrait_4_3` (3:4) —
  see `src/lib/fal/lora-pipeline.ts`'s `SceneGenerationInput.imageSize`.
- Static character portraits on disk are ~2:3 (784×1168, confirmed via
  `file public/images/characters/*.jpg`).

Squeezing a 2:3–3:4 portrait into a 1:1 square with `object-cover` crops
away roughly **25–50% of the image's height** (confirmed by the math: for
a 0.671 aspect ratio, `object-cover` into a square crops ~49% of the
vertical extent) — a real photo of a person rendered with the top and/or
bottom cut off. That's the "half seen" symptom.

Generated video, on the other hand, genuinely *is* square — Kling's
`aspect_ratio` is a hard `'1:1'` enum (`src/lib/fal/animate-portrait.ts`).

**Fix:** the thumbnail container now matches each media type's real shape
instead of one fixed box for both — `aspect-square` for video, `aspect-[3/4]`
for images.

## 2. Chat scroll — "no down navigation"

**File:** `src/components/chat/chat-window.tsx`

**Root cause (two parts):**
- The auto-scroll effect only ran when `messages` or `streamingText`
  changed. A photo/video attached to a message loads *asynchronously* and
  grows the transcript's height after that effect already fired — so a
  reader sitting at the bottom would silently fall out of view the moment
  a photo finished loading, with no way back down except scrolling
  manually.
- The very first scroll-to-bottom (opening a conversation) used the same
  `smooth` animation as a new message arriving, which visibly starts the
  chat scrolled up and drifts down — it *looks* like you have to scroll to
  reach the latest message even though the app is about to do it for you.

**Fix:**
- Added a `ResizeObserver` on the message-list wrapper that re-pins to the
  bottom on *any* height change (new bubble, image finishing a load, a
  "thought" chip expanding) whenever the reader is already near the
  bottom — not just on the two triggers the old effect covered.
- The first scroll-to-bottom on mount now snaps instantly instead of
  animating; every scroll after that still animates normally.

The existing "you scrolled up, here's a New Message pill" behavior for
someone deliberately re-reading earlier messages is unchanged — this only
fixes the case where you're at the bottom and get silently knocked out of
place by content growing beneath you.

## 3. Image added to the visitor homepage

**Files:** `src/components/home/landing-page.tsx`,
`public/images/character-intelligence-visual.svg` (new)

`landing-page.tsx` is the actual logged-out homepage (rendered by
`src/app/(app)/page.tsx` when there's no session). It already had a hero
character portrait and photo cards, but the "Character intelligence"
section and everything after it down to "How it works" was pure text/icon
cards — the first fully text-only stretch a first-time visitor hits after
the hero.

Added a new abstract network/node illustration (built from scratch, not a
character photo — matches the section's own theme of persistent memory/
personality/relationships as connected state) next to that section's
heading. It's a plain `<img>`, not `next/image`/`SafeImage` — this repo's
`next.config.js` deliberately does not set `images.dangerouslyAllowSVG`
(see the existing `ARCH-06` test's comment on `CHARACTER_IMAGE_FALLBACK`
for why: it would open next/image's optimizer to SVG site-wide, including
untrusted AI-generated content, just to render one static asset), so an
SVG has to bypass the optimizer rather than 400 the way that placeholder
attempt once did.

## Not fixed / needs your input

While auditing the image pipeline I found a pre-existing operational note
in `.env.example` worth double-checking against your actual deployment:
if `NEXT_PUBLIC_R2_PUBLIC_URL` / `R2_PUBLIC_URL` aren't set correctly in
production, every character image silently falls back to the generic
placeholder icon (no error, just the fallback avatar) — that's a
deployment config issue, not something a code change can fix. Worth a
quick check of your production env vars if you're ever seeing *every*
character show the same generic icon rather than a cropped photo.
